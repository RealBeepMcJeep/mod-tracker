# Goal: Fully Automated Six-Hour Mod-Tracker Passes

Build and enable a deterministic, stdlib-only, fail-closed automation pipeline for the five-game mod tracker. It must refresh and publish verified reports every six hours while deferring uncertain Nexus Mods ↔ Thunderstore mod and author mappings to a durable interactive review queue.

## Approved behavior

### Scheduled full pass

1. Run at 12:00 AM, 6:00 AM, 12:00 PM, and 6:00 PM in `America/Phoenix`.
2. Collect every required provider for every configured game. Any required provider/game failure aborts generation and publication and preserves the prior live site.
3. Discover bounded mod candidates and author-only candidates after collection.
4. Queue unseen candidates atomically and leave them unmapped. New candidates do not block generation or publication.
5. Generate and strictly verify every report using approved mappings only.
6. Abort publication when a game's card-count change is both greater than 10% and at least 25 cards unless an explicit one-run override is recorded.
7. Run from isolated clean worktrees under one shared nonblocking lock. Abort safely on remote divergence or a non-fast-forward push; never auto-rebase scheduled changes.
8. Commit and push verified tracker changes, publish through the existing `public-artifacts` publisher, push that repository, and verify the exact live routes.
9. If generated bytes are unchanged, skip empty commits and deployment but still run verification and report success.
10. If the verified tracker commit succeeds but publication/deployment fails, keep the tracker commit, preserve the prior live site where possible, report the partial failure, and retry publication later. Never auto-revert a verified tracker commit.
11. Send a compact Telegram summary after every run, highlighting failures and newly pending candidates.

### Deferred mapping queue

1. Support both cross-provider mod candidates and independent author-identity candidates.
2. Persist the live queue as an atomic local flat file plus an append-only event history; do not use a database.
3. Give every candidate a stable identity and evidence fingerprint. Track first seen, last seen, source run IDs, scores, source keys, titles/handles, URLs, bounded evidence, status, and status history.
4. Keep unresolved candidates until explicitly decided and deduplicate them across runs.
5. Reopen a previously rejected candidate when its title, author, URLs, or evidence text materially changes.
6. Queue at most 20 new mod candidates and 20 new author candidates per game per run. Later runs must exclude already queued/decided fingerprints so lower-ranked unseen tranches eventually surface.
7. Pending mappings remain separate source-scoped identities; reports may temporarily contain separate provider cards for one underlying mod until review.
8. Accepted/rejected decisions, rationale, evidence, and confidence become version-controlled review records.

### Interactive LLM reconciliation

1. Start only when requested by the user in the originating Telegram thread.
2. Present at most five candidates per batch, ordered oldest pending first and then by descending candidate score.
3. The LLM researches available evidence and recommends two decisions independently where applicable:
   - `same_mod`
   - `same_author`
4. Attach a separate advisory confidence to each recommendation: `high`, `medium`, or `low`, plus a concise rationale describing supporting evidence and uncertainty.
5. Confidence is an LLM inference, not an automatic authority. It must never apply a mapping or replace evidence.
6. The user explicitly confirms every mod and author decision. A confirmed mod relationship does not imply an author alias, and differing mods do not preclude a separately evidenced author identity.
7. After a confirmed batch, apply decisions atomically, validate reciprocal mappings, regenerate all affected artifacts, strictly verify, commit, push, publish, and verify live immediately under the shared lock.

### Client-side report pagination

1. Keep exactly one self-contained HTML file per game report; do not create page files or server endpoints.
2. Paginate the current filtered result set in fixed increments of 100 cards.
3. Pinned cards count toward the 100-card page size.
4. Provide accessible Previous and Next controls plus a page indicator.
5. Search, sort, category, source, NSFW, update-date, and other filters operate over the complete card set before pagination.
6. Any filter or sort change resets to page 1.
7. Strict verification must bind and validate the pagination markup, behavior, and canonical client script.

### Logging and retention

1. Create a durable project-local run directory for every invocation, including interrupted and failed runs.
2. Record run ID, start/end timestamps, stage status and duration, sanitized command arguments, separate stdout/stderr, provider counts and pagination evidence, candidate queue changes, queue snapshot, report counts, anomaly results, Git SHAs, publication manifest, deployment/version output, live checks, and final `summary.json`.
3. Never log credentials, authorization headers, API-key values, cookies, or secret-bearing environments/commands.
4. Retain detailed logs for 90 days and always keep at least the latest 100 runs.
5. Make log/state/lock paths injectable for isolated tests and ignore runtime state in Git.

## Definition of done

- Every new behavior has a test that was observed failing before implementation and passing afterward.
- `python3 -m unittest discover -s tests -v`, Python compilation, JSON validation, stdlib import audit, deterministic candidate checks, `git diff --check`, and `python3 tracker.py verify --game all --output-root .` all pass.
- Generated reports remain single-file HTML, show no more than 100 matching cards per client-side page, expose working accessible pagination controls, and pass strict tamper tests.
- Candidate queuing never edits authoritative mappings; approved application produces valid reciprocal mod/author mappings only after explicit user confirmation.
- Interactive recommendations preserve distinct mod/author decisions and distinct `high`/`medium`/`low` confidence plus rationale for each.
- Scheduled runs cannot overlap manual automation or review application and cannot publish partial collections or suspicious count changes.
- Every run has reviewable, sanitized, retained diagnostics and emits an accurate compact Telegram summary.
- Automatic commits, pushes, publication, and live verification are proven on the real scheduled path; partial cross-repository failures are accurately recorded and recoverable.
- Both repositories finish clean and synchronized with their respective `origin/main` branches.
- The exact `/mod-tracking/` landing page and all five game routes return the verified current artifacts; an unknown route returns HTTP 404.
- The Hermes job is a verified no-agent script job scheduled at `0 */6 * * *` for Phoenix time and is enabled only after the paused rehearsal passes.
